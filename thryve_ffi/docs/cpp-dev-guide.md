## Prerequisites

Before you begin, ensure you have the following installed:

- **C++17 compatible compiler** (MSVC, GCC, or Clang)
- **CMake 3.15+** (optional, for building with CMake)
- **Rust toolchain** (if you need to build the FFI library yourself)

---

## Installation

### Option 1: Using Pre-built Distribution

If someone has already built the FFI library, you'll receive a distribution package with the following structure:

```
thryve_ffi/
├── include/
│   ├── thryve.h        # C header (generated by cbindgen)
│   └── thryve_ffi.h    # C++ wrapper header (generated by build.rs)
├── lib/
│   └── thryve_ffi.lib  # Import library (Windows)
├── bin/
│   └── thryve_ffi.dll  # Shared library (Windows)
└── examples/
    └── MyThryveApp/
        ├── main.cpp    # Example application
        └── CMakeLists.txt
```

### Option 2: Building from Source

If you need to build the FFI library yourself:

1. **Clone the Thryve repository:**
   ```bash
   git clone https://github.com/your-org/thryve.git
   cd thryve
   ```

2. **Build the FFI library:**
   ```bash
   cargo build --package thryve_ffi        # Debug build
   # or
   cargo build --package thryve_ffi --release  # Release build
   ```

3. **The distribution files will be generated automatically:**
    - Headers: `thryve_ffi/out/` (for IDE support) or `thryve_ffi/dist/include/` (for distribution)
    - DLL: `thryve_ffi/dist/bin/`
    - Import library: `thryve_ffi/dist/lib/`

## Project Setup

Create a new C++ project in your workspace:

```
my_thryve_app/
├── include/
│   ├── thryve.h        # Copy from thryve_ffi/out/ or dist/include/
│   └── thryve_ffi.h    # Copy from thryve_ffi/out/ or dist/include/
├── lib/
│   └── thryve_ffi.lib  # Copy from dist/lib/ (Windows)
├── src/
│   └── main.cpp        # Your application code
├── CMakeLists.txt      # Build configuration
└── README.md           # Project documentation
```

### Setting up the headers

Copy the headers from the FFI distribution to your project:

```bash
# From the Thryve FFI distribution directory (option 1: dist/)
cp dist/include/thryve.h my_thryve_app/include/
cp dist/include/thryve_ffi.h my_thryve_app/include/

# Or from the stable output directory (option 2: out/)
cp ../thryve_ffi/out/thryve.h my_thryve_app/include/
cp ../thryve_ffi/out/thryve_ffi.h my_thryve_app/include/
```

### Setting up the library

Copy the import library to your project:

```bash
# Windows (MSVC)
cp dist/lib/thryve_ffi.lib my_thryve_app/lib/

# Linux
cp dist/lib/libthryve_ffi.a my_thryve_app/lib/

# macOS
cp dist/lib/libthryve_ffi.dylib my_thryve_app/lib/
```

### Setting up the DLL (Windows only)

You need to copy the DLL to your application's output directory:

```bash
# Copy to your build output directory
cp dist/bin/thryve_ffi.dll my_thryve_app/build/
```

## Building

### Using CMake

Create a `CMakeLists.txt` in your project root:

```cmake
cmake_minimum_required(VERSION 3.15)
project(MyThryveApp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# Add include directory for headers (from thryve_ffi/out/ or dist/include/)
include_directories(${CMAKE_SOURCE_DIR}/include)

# Find the source files
file(GLOB SOURCES "src/*.cpp")

# Create the executable
add_executable(${PROJECT_NAME} ${SOURCES})

# Link against the Thryve FFI library
target_link_libraries(${PROJECT_NAME} PRIVATE thryve_ffi)

# On Windows, add the lib directory for the import library and copy DLL
if(WIN32)
    target_link_directories(${PROJECT_NAME} PRIVATE ${CMAKE_SOURCE_DIR}/lib)
    
    # Copy DLL to output directory (from dist/bin/)
    add_custom_command(TARGET ${PROJECT_NAME} POST_BUILD
        COMMAND ${CMAKE_COMMAND} -E copy_if_different
            ${CMAKE_SOURCE_DIR}/../dist/bin/thryve_ffi.dll
            $<TARGET_FILE_DIR:${PROJECT_NAME}>
        COMMENT "Copying thryve_ffi.dll to output directory"
    )
endif()

# On Linux/macOS, add the lib directory for the shared library
if(UNIX AND NOT WIN32)
    target_link_directories(${PROJECT_NAME} PRIVATE ${CMAKE_SOURCE_DIR}/lib)
endif()
```

Build the project:

```bash
mkdir build && cd build
cmake ..
cmake --build . --config Release
```

### Using MSVC (cl.exe)

```bash
# Compile
cl /std:c++17 /Iinclude /EHsc src/main.cpp /link lib/thryve_ffi.lib

# Copy DLL next to executable (from dist/bin/)
copy ..\dist\bin\thryve_ffi.dll .
```

### Using MinGW (g++)

```bash
# Compile
g++ -std=c++17 -Iinclude src/main.cpp -Llib -lthryve_ffi -o my_app.exe

# Copy DLL next to executable (from dist/bin/)
cp ../dist/bin/thryve_ffi.dll .
```

## Writing Your First Plugin

A plugin is a unit of work that runs when the Thryve engine processes it.

### Step 1: Define your plugin callbacks

```cpp
// Plugin cleanup function — called when the plugin is being freed
extern "C" void my_plugin_cleanup(const void* core_ptr) {
    std::cout << "Cleaning up plugin data..." << std::endl;
    // Free your plugin's core data here
}

// Plugin entry point — called when the plugin's task is executed
extern "C" FfiTaskResult my_plugin_entry_point(void) {
    std::cout << "Plugin entry point called!" << std::endl;
    
    // Use the helper function to create a result with proper fields
    FfiTaskResult result = ffi_task_result_new("Success", "Plugin executed", "Main");
    // Or construct manually:
    // FfiTaskResult result = {0};
    // result.result_type = "Success";
    // result.message = "Plugin executed";
    // result.log_file = "Main";
    return result;
}
```

### Step 2: Create the plugin

```cpp
// Create configuration
FfiConfig config = ffi_config_default();
if (!config) {
    std::cerr << "Failed to create config" << std::endl;
    return 1;
}

// Create context
FfiCtx ctx = ffi_ctx_create(config);
if (!ctx) {
    std::cerr << "Failed to create context" << std::endl;
    ffi_config_free(config);
    return 1;
}

// Get the engine's connected PacketHandle from ctx (required for plugin
// creation). Do not create a standalone PacketHandle — it would not be
// wired to this ctx's engine.
FfiPacketHandle packet_handle = ffi_ctx_get_packet_handle(ctx);
if (!packet_handle) {
    std::cerr << "Failed to get packet handle" << std::endl;
    ffi_ctx_free(ctx);
    ffi_config_free(config);
    return 1;
}

// Create the plugin
FfiPlugin plugin = ffi_plugin_create(
    "MyPlugin",           // name
    "MyType",             // type
    nullptr,              // plg_core_ptr (optional, can be NULL)
    packet_handle,        // tx (packet handle - REQUIRED)
    my_plugin_cleanup,    // clean_up callback
    my_plugin_entry_point // entry_point callback
);

if (!plugin) {
    std::cerr << "Failed to create plugin" << std::endl;
    ffi_packet_handle_free(packet_handle);
    ffi_ctx_free(ctx);
    ffi_config_free(config);
    return 1;
}
```

### Step 3: Add the plugin to the context

```cpp
// Add plugin to context (takes ownership of the plugin)
FfiStatus status = ffi_ctx_add_plugin(ctx, plugin);
if (status != FfiStatus_Ok) {
    std::cerr << "Failed to add plugin to context: " << (int)status << std::endl;
    ffi_plugin_free(plugin);  // Free if not added to context
    ffi_packet_handle_free(packet_handle);
    ffi_ctx_free(ctx);
    ffi_config_free(config);
    return 1;
}
std::cout << "Plugin added to context" << std::endl;
```

## Writing Your First Observer

An observer is a unit that runs continuously in the engine's main loop.

### Step 1: Define your observer callbacks

```cpp
// Observer cleanup function — called when the observer is being freed
extern "C" void my_observer_cleanup(const void* core_ptr) {
    std::cout << "Cleaning up observer data..." << std::endl;
}

// Observer job function — called when the observer runs
extern "C" void my_observer_job(FfiObserver observer) {
    std::cout << "Observer job called" << std::endl;
    
    // IMPORTANT: Free the observer when done to prevent memory leaks
    ffi_observer_free(observer);
}
```

### Step 2: Create the observer

```cpp
FfiObserver observer = ffi_observer_create(
    "MyObserver",         // name
    "MyType",             // type
    nullptr,              // obs_core_ptr (optional, can be NULL)
    packet_handle,        // tx (packet handle - REQUIRED)
    my_observer_cleanup,  // clean_up callback
    my_observer_job       // obs_job callback
);

if (!observer) {
    std::cerr << "Failed to create observer" << std::endl;
} else {
    std::cout << "Observer created" << std::endl;
    
    // Add observer to context
    FfiStatus status = ffi_ctx_add_observer(ctx, observer);
    if (status != FfiStatus_Ok) {
        std::cerr << "Failed to add observer to context: " << (int)status << std::endl;
    } else {
        std::cout << "Observer added to context" << std::endl;
    }
}
```

## Common Patterns

### Creating a Task

```cpp
// Define a task job function
extern "C" FfiTaskResult my_task_job(void) {
    std::cout << "Task job called!" << std::endl;
    
    FfiTaskResult result = {0};
    // Your task logic here
    return result;
}

// Create the task
FfiTask task = ffi_task_create(
    "MyTask",             // name
    0,                    // priority (0-255)
    my_task_job           // job callback
);

if (task) {
    // Send the task to the context. ffi_ctx_send_task takes ownership of
    // task — do NOT call ffi_task_free on it afterward, that's a double-free.
    ffi_ctx_send_task(ctx, task);
}
```

### Sending a Notification

```cpp
// Create a notification
FfiNotif notif = ffi_notification_create(
    "MyNotificationType",  // type
    "MyReceiver",          // receiver
    nullptr                // notif_core_ptr (optional)
);

if (notif) {
    // Send the notification to the context. ffi_ctx_send_notification takes
    // ownership of notif — do NOT call ffi_notification_free on it afterward,
    // that's a double-free.
    FfiStatus status = ffi_ctx_send_notification(ctx, notif);
    if (status != FfiStatus_Ok) {
        std::cerr << "Failed to send notification: " << (int)status << std::endl;
    }
}
```

### Starting the Engine

`ffi_run_interactive_start` spawns the engine on a background thread and returns immediately — it does not block. There is no separate "stop" FFI call: the engine's loop only exits once a task result comes back with `result_type = "Fin"` (or `"FinErr"`), which is what actually sets the engine's exit flag. `ffi_run_interactive_free` just waits (joins) for that to happen — call it too early (before any Fin task has been processed) and it blocks forever.

```cpp
// A task job that requests a graceful shutdown once submitted
extern "C" FfiTaskResult shutdown_task_job(void) {
    return ffi_task_result_new("Fin", "Shutting down", "Main");
}

// Start the interactive engine
std::cout << "Starting Thryve engine..." << std::endl;

FfiRunHandle handle = ffi_run_interactive_start(ctx);
if (handle) {
    std::cout << "Engine started. Press Enter to stop..." << std::endl;
    std::cin.get();

    // Submit a shutdown task so the engine actually finalizes and its loop
    // exits — without this, ffi_run_interactive_free below would hang.
    FfiTask shutdown_task = ffi_task_create("Shutdown", 0, shutdown_task_job);
    if (shutdown_task) {
        ffi_packet_handle_send_task(packet_handle, shutdown_task);
    }

    // Now safe to call — returns once the engine thread has processed the
    // shutdown task and exited its loop.
    ffi_run_interactive_free(handle);
}
```

### Complete Example (Interactive Mode)

```cpp
#include "thryve_ffi.h"
#include <iostream>

// Plugin callbacks
extern "C" void plugin_cleanup(const void* core_ptr) {
    std::cout << "Plugin cleanup" << std::endl;
}

extern "C" FfiTaskResult plugin_entry(void) {
    std::cout << "Plugin entry point" << std::endl;
    // Use the helper function to create a result with proper fields
    return ffi_task_result_new("Success", "Plugin executed", "Main");
    // Or construct manually:
    // FfiTaskResult result = {0};
    // result.result_type = "Success";
    // result.message = "Plugin executed";
    // result.log_file = "Main";
    // return result;
}

// Observer callbacks
extern "C" void observer_cleanup(const void* core_ptr) {
    std::cout << "Observer cleanup" << std::endl;
}

extern "C" void observer_job(FfiObserver obs) {
    std::cout << "Observer job" << std::endl;
    ffi_observer_free(obs);
}

// Shutdown task job — the only way to make the engine's loop actually exit
extern "C" FfiTaskResult shutdown_task_job(void) {
    return ffi_task_result_new("Fin", "Shutting down", "Main");
}

int main() {
    // 1. Create configuration
    FfiConfig config = ffi_config_default();
    if (!config) return 1;

    // 2. Create context
    FfiCtx ctx = ffi_ctx_create(config);
    if (!ctx) {
        ffi_config_free(config);
        return 1;
    }

    // 3. Get the engine's connected PacketHandle from ctx — save it, it's
    // the only way to reach the engine once ctx is consumed in step 6.
    FfiPacketHandle pkt = ffi_ctx_get_packet_handle(ctx);
    if (!pkt) {
        ffi_ctx_free(ctx);
        ffi_config_free(config);
        return 1;
    }

    // 4. Create and add plugin
    FfiPlugin plugin = ffi_plugin_create(
        "MyPlugin", "MyType", nullptr, pkt,
        plugin_cleanup, plugin_entry
    );
    ffi_ctx_add_plugin(ctx, plugin);

    // 5. Create and add observer
    FfiObserver obs = ffi_observer_create(
        "MyObserver", "MyType", nullptr, pkt,
        observer_cleanup, observer_job
    );
    ffi_ctx_add_observer(ctx, obs);

    // 6. Start the engine. This consumes ctx — never touch or free ctx again
    // after this call.
    FfiRunHandle handle = ffi_run_interactive_start(ctx);
    if (handle) {
        std::cin.get();

        // Submit a shutdown task so the engine actually finalizes and exits
        // its loop — without this, ffi_run_interactive_free below would hang.
        FfiTask shutdown_task = ffi_task_create("Shutdown", 0, shutdown_task_job);
        if (shutdown_task) {
            ffi_packet_handle_send_task(pkt, shutdown_task);
        }

        ffi_run_interactive_free(handle);
    }

    // 7. Cleanup
    ffi_packet_handle_free(pkt);
    // NOTE: ctx was consumed by ffi_run_interactive_start, so don't free it
    // NOTE: plugin and observer are owned by ctx, so don't free them
    ffi_config_free(config);

    return 0;
}
```

## Running as a Windows Service

To run the Thryve engine as a Windows service, use `ffi_service_create` and `ffi_service_run` instead of `ffi_run_interactive_start`. The service mode is designed for background execution managed by the Windows Service Control Manager (SCM).

### Starting the Service

```cpp
// 1. Create configuration
FfiConfig config = ffi_config_default();
if (!config) return 1;

// 2. Create the service instance. This also builds its matching ctx and
// returns both together — there's no separate ffi_ctx_create call for
// service mode, unlike interactive mode.
FfiServiceCreateResult created = ffi_service_create(config);
if (!created.service || !created.ctx) {
    ffi_config_free(config);
    return 1;
}
FfiService service = created.service;
FfiCtx ctx = created.ctx;

// 3. Get the engine's connected PacketHandle from ctx (required to create
// plugins/observers)
FfiPacketHandle pkt = ffi_ctx_get_packet_handle(ctx);
if (!pkt) {
    ffi_service_free(service);
    ffi_ctx_free(ctx);
    ffi_config_free(config);
    return 1;
}

// 4. Add plugins/observers to the context
// ... add plugin and observer as shown above ...

// 5. Start the service (blocks until SCM sends Stop)
// ffi_service_run is a BLOCKING call that registers with the Windows SCM.
// The engine thread is spawned inside ffi_service_run when SCM sends Start.
// ffi_service_run only returns when SCM sends Stop.
FfiStatus status = ffi_service_run(service, ctx);
if (status != FfiStatus_Ok) {
    std::cerr << "Service run failed: " << (int)status << std::endl;
}

// NOTE: After ffi_service_run returns, both `service` and `ctx` are already
// consumed (they become Box::from_raw inside ffi_service_run and are dropped).
// You do NOT call ffi_service_free or ffi_ctx_free after ffi_service_run.

// 6. Cleanup remaining resources
// Note: plugin is owned by ctx, so don't free it
// Note: ctx was consumed by ffi_service_run, so don't free it
// Note: service was consumed by ffi_service_run, so don't free it
ffi_packet_handle_free(pkt);
ffi_config_free(config);
```

### Service Lifecycle

The service lifecycle is managed by the Windows SCM:

1. **Start**: When the SCM sends `Command::Start`, the service:
   - Spawns the engine in a dedicated thread
   - Loads observers and plugins from the context
   - Starts the main processing loop
2. **Stop**: When the SCM sends `Command::Stop`, the service:
   - Signals the engine to shut down
   - Joins the engine thread (ensures graceful cleanup)
   - Returns from `ffi_service_run`
3. **Pause/Resume**: When the SCM sends `Command::Pause` or `Command::Resume`, the engine suspends/resumes processing

### Installing and Uninstalling the Service

To install the service on Windows:

```bash
# Run as Administrator
ImgCompression.exe install
```

This uses `sc.exe` to register the service with the SCM. The service will start automatically on system boot.

To uninstall:

```bash
# Run as Administrator
ImgCompression.exe uninstall
```

This stops the service (if running) and removes it from the SCM.

### Service vs Interactive Mode Differences

| Aspect | Interactive | Service |
|--------|-------------|---------|
| Engine start | Immediate via `ffi_run_interactive_start` | Deferred until SCM sends `Start` |
| Engine stop | You call `ffi_run_interactive_free` | SCM sends `Stop` command |
| Pause/Resume | Not supported | Supported via SCM |
| After run | **Don't** free `ctx` (consumed by start), free `config` | **Don't** free `ctx` (consumed by run), **don't** free `service` (consumed by run), free `config` |
| Blocking call | `ffi_run_interactive_start` returns `FfiRunHandle` | `ffi_service_run` is blocking, returns `FfiStatus` |

### Complete Example (Service Mode)

```cpp

    ffi_config_free(config);

    return 0;
}
```

## Memory Management

### Ownership Rules

1. **Plugin/Observer creation**: After calling `ffi_plugin_create()` or `ffi_observer_create()`, the plugin/observer is owned by Rust.

2. **Context addition**: After calling `ffi_ctx_add_plugin()` or `ffi_ctx_add_observer()`, the plugin/observer is moved into the context's vectors. **Do not free it** — the context will clean it up.

3. **Observer job callback**: When the observer job callback receives an `FfiObserver`, you **must** call `ffi_observer_free()` on it to prevent memory leaks.

4. **PacketHandle**: Get it from `ffi_ctx_get_packet_handle(ctx)` — this is the engine's real, connected handle. (There is no standalone `ffi_packet_handle_create` — it doesn't exist, and a disconnected packet handle wouldn't reach the engine anyway.) It is cloned inside the Rust side when passed to plugin/observer creation, so you can continue to use your copy afterward.

5. **Sending tasks/notifications**: `ffi_ctx_send_task`, `ffi_ctx_send_notification`, `ffi_packet_handle_send_task`, and `ffi_packet_handle_send_notification` all **take ownership** of the task/notification you pass in. **Do not** call `ffi_task_free`/`ffi_notification_free` on it afterward — that's a double-free.

6. **`ffi_ctx_create` vs `ffi_service_create`**: `ffi_ctx_create(config)` is for **interactive mode** — it's the only way to get a bare `ctx` to populate before starting the engine. **Service mode doesn't use it** — `ffi_service_create(config)` already returns its own matching `ctx` bundled together with the service.

### Service Mode Cleanup

When using `ffi_service_run`, **both** the service and context are **consumed** (not freed) inside the function. This is different from interactive mode where only `ctx` is consumed:

| Resource | Interactive (`ffi_run_interactive_start`) | Service (`ffi_service_run`) |
|----------|------------------------------------------|----------------------------|
| `ctx` | From `ffi_ctx_create` — consumed by start (don't free) | From `ffi_service_create`'s bundled result — consumed by run (don't free) |
| `service` | N/A | From `ffi_service_create` — consumed by run (don't free) |
| `config` | Free with `ffi_config_free` | Free with `ffi_config_free` |
| `packet_handle` | From `ffi_ctx_get_packet_handle(ctx)` — free with `ffi_packet_handle_free` | From `ffi_ctx_get_packet_handle(ctx)` — free with `ffi_packet_handle_free` |

**Important**: After `ffi_service_run` returns, you **must NOT** call:
- `ffi_service_free(service)` — the service was already consumed and dropped inside `ffi_service_run`
- `ffi_ctx_free(ctx)` — the ctx was already consumed and dropped inside `ffi_service_run`

Calling either of these after `ffi_service_run` will result in a **double-free** and undefined behavior.

### Ownership Transfer Diagram

```
Foreign Language                              Rust
──────────────                                ──────
                                              ┌─────────────────────────┐
1. ffi_config_default()                       │ Creates and owns Config   │
   → FfiConfig                                 └─────────────────────────┘
                                              ┌─────────────────────────┐
2. ffi_ctx_create(config)                     │ Creates and owns Ctx      │
   → FfiCtx                                    └─────────────────────────┘
                                              ┌─────────────────────────┐
3. ffi_plugin_create(name, type, core, tx,    │ Takes ownership of:       │
    clean_up, entry_point)                      │ - name (CString)          │
   → FfiPlugin                                 │ - type (CString)          │
                                              │ - entry_point (TaskJob)   │
                                              │ Does NOT take:            │
                                              │ - clean_up                │
                                              │ - plg_core_ptr (passed    │
                                              │   through adapter)        │
                                              └─────────────────────────┘
                                              ┌─────────────────────────┐
4. ffi_ctx_add_plugin(ctx, plugin)            │ Clones plugin into ctx    │
   → FfiStatus                                 │ Does NOT take ownership │
                                              └─────────────────────────┘
```

## Troubleshooting

### Cannot find headers

Make sure the include path points to the directory containing `thryve_ffi.h`:

```bash
# CMake
target_include_directories(my_app PRIVATE ${CMAKE_SOURCE_DIR}/include)

# MSVC
cl /Iinclude main.cpp

# g++
g++ -Iinclude main.cpp
```

### Cannot link against thryve_ffi.lib

Make sure the library path is correct:

```bash
# CMake
target_link_directories(my_app PRIVATE ${CMAKE_SOURCE_DIR}/lib)
target_link_libraries(my_app PRIVATE thryve_ffi)

# MSVC
cl main.cpp /link lib/thryve_ffi.lib

# g++
g++ main.cpp -Llib -lthryve_ffi
```

### DLL not found at runtime (Windows)

Copy `thryve_ffi.dll` to the same directory as your executable:

```bash
# CMake (add to CMakeLists.txt)
add_custom_command(TARGET my_app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_if_different
        ${CMAKE_SOURCE_DIR}/../dist/bin/thryve_ffi.dll
        $<TARGET_FILE_DIR:my_app>
)

# Manual
copy dist\bin\thryve_ffi.dll .
```

### Application crashes on startup

Ensure you're using the correct build configuration:
- Debug build: Use `dist/bin/thryve_ffi.dll` (or copy from `target/debug/thryve_ffi.dll`)
- Release build: Use `dist/bin/thryve_ffi.dll` (or copy from `target/release/thryve_ffi.dll`)

### IntelliSense errors in VS Code

Add the include directory to your `c_cpp_properties.json`:

```json
{
    "configurations": [
        {
            "name": "Win32",
            "includePath": [
                "${workspaceFolder}/**",
                "${workspaceFolder}/include"
            ],
            "defines": ["_DEBUG", "UNICODE", "_UNICODE"],
            "compilerPath": "C:/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/MSVC/14.37.32822/bin/Hostx64/x64/cl.exe",
            "cStandard": "c17",
            "intelliSenseMode": "windows-msvc-x64"
        }
    ],
    "version": 4
}
```

### Header files are out of date

Rebuild the FFI library:

```bash
cargo build --package thryve_ffi --release
```

The headers will be regenerated and copied to `dist/include/`.
